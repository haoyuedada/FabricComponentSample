# 滚动中装配窗口无界扩张 → 提交延迟 → 白屏（flash-list 2.x）

> **给 `@react-native-ohos/flash-list` 维护者的 issue 正文**（可直接使用）
> 环境：HarmonyOS / React Native 0.82 / flash-list 2.1.1-rc.1 · 与社区 #2517 同族
> 附：`upstream_patches/` 内 3 个 patch（已验证可 apply，apply 后与我们工作区字节级一致）

---

## 一、背景

我们在鸿蒙端用 flash-list 2.x 做长列表（303 首的歌单）。**快速连续滚动时列表区域整片变白**，内容消失，但数据与交互都正常 —— 视觉连续性受损，用户感知为"卡死/坏了"。

排查后确认这是 **flash-list 2.x 内部策略**与 **React 渲染队列**共同作用的结果，**不是业务侧用法问题、也不是鸿蒙平台渲染能力不足**（同 App 的 Android 端 60 帧 0 白）。

具体来说：**滚动持续期间，装配窗口的扩张速度跟不上揭示速度**，导致每次提交要渲染的行数持续变大；叠加「每个滚动事件都整窗重建元素」，React 渲染队列无界增长，最终一次提交被拖到数秒 → commit 被压到任务末尾 → 视口内的行始终没被挂载 → 白屏。

Android 端不白屏的原因：它用**原生 ViewHolder 复用**，bind 是同步的，没有"提交队列"这个环节。**鸿蒙 RN 侧有这一环**，所以同样的窗口策略在 RN 上会暴露。

## 二、复现 Demo

### 环境
| 项 | 值 |
|---|---|
| 设备 | LAP-AL10 · HarmonyOS 7 · 1140×2442 |
| App | RN 0.82.30（`@react-native-ohos/react-native-harmony`）· flash-list 2.1.1-rc.1 |
| 列表 | 303 项的可滚动长列表（歌单） |
| 构建 | 本地 release 构建 |

### 注入步骤（鸿蒙）

```bash
# 1) 冷启进列表页（深链接）
hdc shell "aa start -b com.example.app -a EntryAbility -U '<deeplink>'"
sleep 40

# 2) 慢速暖区 ×10 —— 让图片缓存预热（排除冷启动图片未加载的干扰）
for i in $(seq 1 10); do
  hdc shell "uitest uiInput swipe 570 1900 570 1100 200"; sleep 0.7
done

# 3) 快滑深插 ×3 —— 进入冷区（图片未缓存）
for i in $(seq 1 3); do
  hdc shell "uitest uiInput swipe 570 500 570 1900 20000"; sleep 2
done

# 4) ★ 关键：连续快速回滑 ×12，间隔 0.4s（连续、不沉降）
for i in $(seq 1 12); do
  hdc shell "uitest uiInput swipe 570 500 570 1900 20000"; sleep 0.4
done

# 5) 静置 18s —— 看空窗能否自愈
```

> **注入参数的坑（若用 `swipe`）**：`uitest uiInput swipe` 的 `velocity` 参数**不控制速度**
> （实测距离固定 1500px 时，v=600/1500/3000/6000/12000 的耗时分别是 408/2064/1376/711/511ms，
> 与参数无单调关系；真实速度 ≈ 距离/固定插值步数）。
> **要做出真手快滑量级（≈7500px/s）必须用 `uitest uiInput dircFling <dir> <velocity>`**
> （实测 up：3000→600ms · 8000→528ms · 20000→329ms，单调）。
> 我们最初的协议用错了参数，导致一度"复现不出快滑"，这是**指标/协议问题，不是库的问题**。

### 复现率
- **连续**快滑（间隔 <400ms）→ **4/4 轮必现**
- **离散**快滑（间隔 >2s）→ 4 轮里仅 1 轮偶现 → **离散滑测不出来**

> 这是本问题最容易被漏掉的地方：**必须用连续协议**，否则会得到"没有 bug"的结论。

### 观测
录屏（10fps 抽帧）里可见：滚动中列表区域大片变白，白区可达 **96% 视口**（整块列表体未挂载，不是"尾部一条窄带"）。

## 三、发生条件

| 条件 | 阈值 | 说明 |
|---|---|---|
| **滚动连续性** | 相邻快滑间隔 < **400ms** | 最关键。间隔 >2s 时几乎不复现 |
| **揭示速率** | 持续 > **~3000px/s** | 单次快滑不够，需要**持续**高揭示 |
| **列表长度** | 足够长（数百项） | 短列表装配窗口小，撑不住 |
| **白底/浅色主题** | — | 只是让现象**更明显**（空白区与底色同色），非成因 |
| **图片缓存状态** | 冷/热均可 | 冷缓存时更易复现，但不是成因 |

**不构成条件的**（已逐一排除，见下）：

| 排除项 | 判别实验 | 观测 |
|---|---|---|
| 滚动事件没传过去 | trace 数 topScroll | 白闪窗内 **37~41/s 持续到达** → 事件管道正常 |
| 挂载慢 | trace 的 createNode/cloneNode | 白闪窗内 **= 0** → 不是挂载慢，是**还没提交** |
| 图片加载回流 | 布局事件时间配对 | 配对 99%，纯回流候选 0 |
| 业务侧 store 读过多 | 中性化 4 个 store 读 | 渲染 1.19→1.02（**-14%**）→ 非主因 |
| context 穿透 | 中性化 context 读 | 白屏率与对照**完全相同** → 无关 |

## 四、问题（三个叠加的机制）

### ① 装配窗口在持续滚动中无界扩张
`EngagedIndicesTracker` 用 **5 样本多数投票**判定滚动方向。方向反转后需 ~3 个样本（**实测 ~2s**）才翻转缓冲方向，
期间**后向缓冲只有 30%**。

- 反滑开始的头 ~2s，装配窗口仍朝旧方向 → 窗口覆盖不到新露出的区域 → **零装配 = 白屏**
- 持续同向滚动时，窗口随滚动持续前移扩张 → 每个提交要渲染的行数持续变大

### ② 每提交整窗重建元素
`RenderStackManager.sync` 每次滚动事件都把整窗（~17 行）的 key 映射 `delete + set` 一遍，
**已正确绑定的 index 也被重渲**。实测：**每事件 1.18 次 cell 渲染**，而「真正换行」只需 ≈0.33 次 → **放大 3.6×**。

### ③ 提交被 React 渲染队列压后
每个滚动事件都触发一次提交 → 队列无界增长 → **最大单任务 5.2s**（一次提交拖了 5 秒）
→ commit 被压到任务末尾 → 视口内行始终未挂载 → 白屏。

trace 侧证据：白闪窗内 **JS 线程 busy 1000ms/s（饱和）**，其中 `performMicrotaskCheckpoint` 占 2.9s/3s
→ 饱和在 **React 并发渲染微任务循环**，不在挂载。

### 量级对照
| 量 | 值 |
|---|---|
| 需求（p90 揭示速率 ÷ 行高 186px） | **40.1 行/s** |
| 产能（实测每事件 1.18 次 × 40 事件/s） | **~47 行/s** |

> 产能够但仍白屏 → 瓶颈在**时间维度**（峰值段追不上前沿），不是总吞吐。
> 这也是为什么"降低滚动速度"只能缓解、不能根治。

## 五、解决方案（3 个 patch，已验证）

> 目录 `upstream_patches/`，基于 `flash-list@2.1.1-rc.1` 的 npm 原版生成。
> 应用方式（在仓库根目录）：
> ```bash
> npm i @react-native-ohos/flash-list@2.1.1-rc.1
> git apply upstream_patches/P-DIR-FLIP.patch
> git apply upstream_patches/P-INC-SYNC+P-KEEP-POOL.patch
> git apply upstream_patches/P-THROTTLE-COMMIT.patch
> ```
> **已验证**：从 npm 原版 apply 这 3 个 patch 后，产物与我们验证过的版本**字节级一致**。

### patch 1 · `[P-DIR-FLIP]` 方向即时翻转 — `dist/recyclerview/helpers/EngagedIndicesTracker.js`
**问题**：5 样本多数投票 → 方向反转后 ~2s 才翻转，期间后向缓冲仅 30% → 回滑头 2 秒零装配。
**改法**：新样本方向与当前多数判定相反时**立即重置速度史**。
**效果**：回滑 2s 空窗 → **首窗 46 cells**。

### patch 2 · `[P-INC-SYNC]` + `[P-KEEP-POOL]` — `dist/recyclerview/RenderStackManager.js`
**问题**：(a) 每事件整窗重建 key 映射 → 每事件 1.18 次渲染（实际只需 0.33 次）；
(b) 每次同步清空回收池 → "刚滚出、仍可复用"的 cell 被丢弃，新行只能重新挂载（实测 create 588 次里 **263 次**属这种浪费）。
**改法**：(a) 已正确绑定的 index 直接跳过；(b) 不再每次清空回收池（逐 key 校验已处理失效项，清空只留给真正的整体失效场景）。
**效果**：白闪率 **20.7% → 16.5%**（同协议同深度）。

### patch 3 · `[P-THROTTLE-COMMIT]` 提交限 10Hz + 动量末强制提交 — `dist/recyclerview/RecyclerView.js`
**问题**：每事件一次提交 → 队列无界 → 最大巨批 5.2s。
**改法**：滚动中把「推给 React 的提交」节流到 **≤10Hz**；**动量结束时强制提交一次**，补齐节流期间跳过的变更（保证最终态一定上屏）。
**效果**：最大巨批 **5210ms → 1694ms**；挂载从停摆 → 推进；白闪率 **16.5% → 8.3%**。

### 三者叠加
白闪率（帧占比，同协议同深度）：

| 配置 | 白闪率 |
|---|---|
| 基线（无 patch） | **20.7%** |
| + patch1 + patch2 | 16.5% |
| + patch3 | **8.3%** |

### ⚠️ 一个需要上游注意的量化耦合
提交节流与后向缓冲**互斥**：

```
后向缓冲需 ≥ v × 节流间隔 = 2600 × 0.2 = 520px  ⇒  drawDistance ≳ 870
但 drawDistance 越大 → 待渲批量越大 → 提交越晚
```

我们实测 **drawDistance 调大反而更糟**（dd=1000 时灰闪 55~62%，dd=250 时 28~36%）。
→ **dd 是「待渲批量」不是「覆盖量」**，越大越卡。
若上游要提供"平滑快滑"选项，需要给出**缓冲与节流的联合约束**，否则业务侧会踩坑。

## 六、附：ArkUI 惯性曲线的认知（避免上游误配）

我们评测过"用 Android 的幂律 + 样条表近似 ArkUI 惯性"，**实测判负并已回退**：
白闪 6.6% 落在 ArkUI 曲线 n=3 噪声带（5.8~9.1%）内 = **无收益**，且用户体感"滚动发卡"（双驱动 + dt 积分 + 闩锁吞帧）。

顺带纠正一个易混点（**常被搞错**）：

| 平台 | 模型 | 距离 / 时长律 |
|---|---|---|
| iOS | 纯指数衰减 `v(t)=v₀·0.998^t(ms)` | D ≈ v₀×0.5s（∝v₀ 线性）· T ∝ v₀ |
| **Android** | SplineOverScroller：幂律 + **100 点三次样条表** + 飞轮 | **D ∝ v₀^1.736（超线性）** · T ∝ v₀^0.736 |
| **ArkUI（鸿蒙）** | friction 摩擦系数模型（公式未公开） | 固定 friction 下 **D ∝ v₀（线性）· T ∝ ln v₀** |

→ 「D ∝ v₀^1.74」是 **Android** 的律，**不是 ArkUI 的**。ArkUI 固定 friction 下是线性的。
